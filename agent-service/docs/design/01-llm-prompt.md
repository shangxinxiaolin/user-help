# LLM 接入与 Prompt 工程

> 一切的起点：接上第一个 LLM，跑通流式输出与多轮对话。地基不牢，后面所有模块都搭不稳。

## 背景与问题

智能客服的第一步是把大模型接进系统：用户发一句、模型回一句。看似简单，实际要解决三件事——怎么调模型、怎么把对话历史喂回去、怎么做到逐字流式返回。

## 设计

- **模型调用**：用 LangChain 的 `ChatOpenAI` 封装模型调用，`PromptTemplate` 管理提示词，结构化输出原语约束返回格式。
- **流式输出**：回答逐字吐给用户，不等整段生成完（这是客服体验的底线）。
- **多轮对话最简版**：把历史消息按原顺序拼进 `messages`，再用两招防止无限长——按轮数留最近几轮 + 按 token 预算裁掉最老的（滑动窗口）。

```text
messages = [SystemMessage(...)]
  + 最近 N 轮历史（按序）
  + [HumanMessage(当前问题)]
```

## 选型理由

| 选型 | 理由 |
|---|---|
| LangChain | 封装了 `ChatOpenAI` / `PromptTemplate` / 结构化输出，接模型和做 Prompt 工程绕不开它 |
| 模型切换靠 `.env` | 上游地址、模型名、密钥收进配置，换模型只改配置、不动代码 |

## 关键结论与坑

- **前缀缓存**：`system` 段（人设 + 红线 + 工具定义）每轮逐字不变，才能命中模型服务商的缓存；把每轮可变的内容塞进 `system` 会当场击穿缓存。
- **滑窗"够用先跑"**：第一章的最简滑窗刻意从简，它的短板（扛不住用户回翻旧话题）留给上下文管理那一章填，这里先跑通链路即可。
- **模型是能换的**：不要在代码里写死某个模型，为后面"先求准、再求省"的降本路径留口子。
