# 可观测性与数据飞轮

> 前半照亮黑盒（trace 树 + Langfuse + 评估流水线防退化 + 成本控制），后半接住答不上来的问题（三入口 → 标准化查重 → 三道闸 → 写回知识库）。

## 背景与问题

上线一周，老板两个问题：①某用户收到离谱回答，哪一步出的岔子？②这个月 token 花超了，钱花哪了？答案都埋在那个"每步想了啥、调了哪个工具、花了多少 token"没人留痕的黑盒里。

## 设计

### 可观测性

- **trace 树 / span**：一次请求 = 一棵树根，每个节点（模型调用/工具调用/检索）是一个 span，谁调谁、先后、耗时一目了然。
- **Langfuse 零侵入**：三个环境变量 + 编译时挂一次 `CallbackHandler`，节点代码一行不动。
- **自动化评估流水线**：拿 RAG 那套评估集定期回归（每天/每次改动），分数连成趋势线，拐头报警——防悄悄退化。
- **Cost Control**：按意图汇总 token，哪类意图最烧钱现形；高频简单意图（物流/订单）换小模型，复杂意图（商品咨询/退款/售后）留大模型。

### 数据飞轮

```text
三入口 ──┐
  ①证据置信度低 ─┤
  ②useful=false ─┼→ 低置信度问题池 → 标准化+查重(累加频次)
  ③用户反馈没解决 ┘      → 三道闸审核 → 向量化写回知识库
```

## 选型理由

- **Langfuse 开源自部署**：数据不出境、能自部署，顺着整套"数据不出境"选型立场；不介意上云换 LangChain 同源的 LangSmith（连回调都不用挂）。

## 关键结论与坑

- **三入口互补**：`evidence_confidence` 看检索证据强弱（检索侧），`useful` 看证据能否支撑回答（生成侧），用户反馈抓"系统自以为答对其实没解决"（隐蔽那类）。
- **三道闸**：垃圾过滤、时效过期、低频冷门——机器判的低置信度混着不该入库的东西，得靠人筛。
- **累加频次是宝贵信号**：一个缺口被越多用户问，越该优先补。
- **趋势线比单次分数更重要**：盯的是"有没有往下掉"，不是某次考多少分。
