# Function Call 工具调用

> 让模型从"只会说"变成"会查"：给它一把工具，它自己决定调哪个、带着什么参数。

## 背景与问题

用户问"我的订单到哪了"，模型训练语料里没有这笔订单。系统得给模型配工具，让它能查订单、查物流。这一章的起点是最简单的形式：模型单轮判断要不要调工具、调哪个。

## 设计

- **工具清单 + 注册表**：`TOOL_REGISTRY` 维护一份工具名到实现的映射，模型回复里带 `tool_calls` 就按名取工具执行。
- **单轮调用链路**：

```text
用户消息 → LLM（带工具定义）→ ai_msg
  ├─ 有 tool_calls → 逐个执行 → 结果塞回 messages → （第一章版本到此为止）
  └─ 无 tool_calls → 直接当最终答案返回
```

- **内置工具**：查订单、查物流、查商品等，写死在代码里（`app/tools/`）。

## 选型理由

- **写死内置工具够课程跑**：五个常用工具能覆盖演示场景。
- **但生产不够**：真实客服要接物流系统、仓储系统、第三方查询，每接一个都改代码、重启服务——这正是后面"工具系统（MCP）"要解决的动机。

## 关键结论与坑

- **单轮调用的局限**：用户报手机号查物流，模型先查订单拿到物流单号、再拿单号查物流——这一步需要两次工具调用。单轮版本走到"查订单"就没了下文，只能等用户再推一句。
- **答案就是外面套个 `for` 循环**：让模型想调几次调几次，这就是 ReAct 的雏形（详见 Workflow + Agent 混合架构那一章）。第一章留的那个"第二次工具调用不再接"的问号，答案就是这十来行代码。
