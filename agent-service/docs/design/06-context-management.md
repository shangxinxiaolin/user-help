# 会话上下文分层管理

> 会话内"越近越完整、越远压得越狠"的三层分层，解决纯滑窗扛不住用户回翻旧话题的问题。

## 背景与问题

纯滑窗只认位置不认内容：用户聊了十几轮后忽然问"我之前那个耳机能改地址吗"，最开头的"蓝牙耳机 A"那轮早被挤出窗口扔掉了，指代消解翻历史找不到着落。

## 设计（会话内三层）

```text
历史消息（按自增 id 排序）
  ├─ 层1 最近 N 轮：原文一字不压（context_window_turns=8）
  │     指代消解/意图判断靠精确措辞，近处必须保真
  ├─ 层2 中间：规则截短，不调模型
  │     用户原话不动；客服答复只留开头几十字；大工具结果换一行标识
  └─ 层3 远处：后台异步摘要（一段段攒、压完定死不回头重写）
```

- **三种选历史法**：滑动窗口（位置，打底）/ 语义检索（内容，捞远处）/ 主题重要度（关键事实留底）。本项目只把滑窗做扎实，另两种按需加。
- **额度从窗口倒推**：`历史预算 = min(N × (X+Y), 窗口 - 固定开销)`，层1 七成、层2 三成，不写死常量。
- **State 边界**：`messages` 只进不出（事实源 + checkpoint，`add_messages` 自动追加），分层动的是每轮现拼的精简版，靠两个 id 切三段、只挪数字不搬数据。

## 选型理由

- **截断 vs 摘要**：截断省 token 丢信息，摘要保信息多一次模型调用；客服早期常埋订单号/诉求，摘要值得。
- **中间层用规则不调模型**：轻的手段扛得住就别动用贵的。
- **摘要看用量不数条数**：工具结果不落消息表，数条数看不见它涨。

## 关键结论与坑

- **摘要一段段攒、压完定死不回头重写**：否则订单号会被反复有损压缩磨掉。
- **中文 token 口径**：默认 4 字符=1 token 是英文口径，中文 1 字≈1 token；裁剪闸门与预算用同一校准口径，全链路只走一个换算入口（统一当除数）。
- **摘要/证据别塞进 system**：否则前缀缓存命中归零（实测撞出来的坑）。
- **只管当前这一通会话**：不跨会话、不攒用户画像。
